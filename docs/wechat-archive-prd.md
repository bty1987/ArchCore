## 1. 背景与目标

### 1.1 业务背景

团队与客户的日常沟通大量发生在微信（以**项目群**为主）。当前痛点：

- 沟通记录散落在员工个人微信中，人员流动即记录流失，无沉淀；
- 管理者无法了解各客户群的沟通活跃度、响应质量与风险信号；
- 客户沉默、投诉前兆、关键成员退群等信号无人盯，错失干预时机。

因 Wechaty token 等协议服务已不可购买（见调研报告），采用**本地客户端采集**路线：以本地数据库解密获取历史记录为主轨，hook 实时回调为增强轨。

### 1.2 产品目标

1. **沉淀**：将持续采集的微信群/单聊消息结构化归档，形成客户沟通资产；
2. **分析**：以「**一个群 ≈ 一个客户**」为核心模型，提供办公视角的客户沟通分析；
3. **预警**：对沉默客户、响应超时、风险关键词等信号实时预警并通知负责人；
4. **管理**：提供一个内网 Web 管理台，覆盖分析、记录检索、预警处理全流程。

### 1.3 非目标（本期不做）

- 不做营销群发、自动回复等外向自动化（外发默认**永久只收不发**，见 4.8 与《主动推送消息方案》）；
- 不做手机端（管理台为桌面 Web，响应式适配即可）；
- 不做跨平台归档（QQ/钉钉等不在范围）；
- 不做员工个人账号消息采集（单采集号架构，多采集端扩展为 V2+ 评估项，见 3.1 采集账号定位）；
- 不承诺微信 4.x 客户端支持（跟随工具生态演进，见第 7 节）。

## 2. 用户与角色

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| 管理者/主管 | 查看全部客户与预警 | 总览健康度、及时收到预警、抽查沟通质量 |
| 销售/负责人 | 只看自己负责的客户 | 回顾历史沟通、客户动态、处理自己的预警 |
| 系统管理员 | 维护采集端与配置 | 采集任务稳定运行、成员名单与映射维护 |
| 超级管理员 | 全部权限 + 审计 | 账号权限、操作日志、数据安全 |

## 3. 核心概念与数据模型

### 3.1 概念

- **客户（Customer）**：归档与分析的主体，通常对应一个甲方/合作方；
- **群（GroupChat）**：微信群。**核心映射：一个群归属一个客户**；一个客户可关联多个群（售前群/项目群/售后群）；
- **单聊（DM）**：员工与客户方联系人的私聊，联系人可选择性挂到客户下；
- **我方成员 / 客户方成员**：群内成员按配置的内部名单（微信号/昵称/备注匹配）二分，是响应时效等指标的计算基础；
- **采集账号（采集号）**：登录在采集主机上的专用微信号，是唯一数据入口。当前为**单采集号架构**：归档范围 = 该号所在的白名单业务群 + 该号自身的客户单聊。员工个人账号与客户的单聊**不在采集范围**（需多采集端，V2+ 评估）。「一个群 ≈ 一个客户」模型不受影响——群消息对采集号全量可见。

### 3.2 实体关系

```
Customer 1 ── n GroupChat 1 ── n Message
Customer 1 ── n Contact 1 ── n Message(单聊)
Message: 群ID/会话ID、发送者、方向(我方/客户方)、类型、时间、内容、媒体引用
AlertRule 1 ── n Alert ── n NotifyRecord
```

### 3.3 消息类型处理

| 类型 | 归档策略 | 检索/分析 |
|---|---|---|
| 文本 | 全文入库 | 全文检索、关键词、话题分析 |
| 图片/视频/语音 | 存媒体文件 + 元数据（大小/时长） | 可检索占位、不计入文本分析；语音转文字列为 V2 |
| 文件 | 存文件 + 文件名 | 文件名可检索（合同/报价单识别） |
| 引用/表情等 | 存结构化 JSON | 展示还原，不参与分析 |
| 撤回消息 | 解密库有残留则入库并标记 `recalled`（4.x 真机已验证残留可得） | 撤回前内容仅限管理员可见（审计价值），不计入分析 |
| 红包/转账 | 存系统占位与可得元数据（金额/状态） | 仅流水展示，不入分析 |
| 系统消息 | 入库（进群/退群/群改名等） | 群成员异动比对的输入 |

> 撤回/红包/转账/系统消息的具体残留口径以 M0 验证 #9 结论为准（调研报告第九节）。

## 4. 功能需求

优先级：P0 = MVP 必须；P1 = V1；P2 = 增强/可选。

### 4.1 数据采集（F1）

## 5. 关键用户流程

1. **首次接入**：管理员配置内部成员名单 → 执行历史导入 → 待认领群列表人工映射到客户 → 数据看板可用；
2. **日常运营**：采集端定时/实时同步 → 预警引擎扫描 → 命中规则推送通知 → 负责人在预警中心处理并留痕；
3. **管理者抽查**：仪表盘发现红色客户 → 进入客户详情 → 会话浏览器检索上下文 → 必要时导出留档。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 部署 | 内网部署。采集端必须与登录微信的 Windows 主机同机；Web 服务可同机或内网独立服务器 |
| 存储 | SQLite 起步（与调研一致），schema 预留迁移 MySQL/PostgreSQL；媒体文件独立目录 + 定期备份 |
| 性能 | 10 万条消息组合检索 < 2s；历史导入 ≥ 1 万条/分钟；页面首屏 < 3s |
| 安全 | 会话数据为高敏数据：本地存储不出内网、账号角色权限（4.2 节角色）、管理台全操作审计日志、数据库可选加密 |
| 合规 | 用途限定内部客户管理与风控；员工知情沟通并留存制度依据；客户方成员（第三方个人信息主体）的告知与最小化措施见[合规方案](compliance-plan.md)；不做任何对外提供数据的接口 |
| 可维护 | 微信版本 + 采集工具版本组合固化并文档化；工具断供时可整体离线重部署 |

## 7. 技术约束与依赖（摘要自调研报告）

1. **主轨为本地 DB 解密**（PyWxDump/WeChatDataAnalysis）：不依赖 **3.9.x 旧版**登录窗口（可随工具生态切 4.x），但**同样依赖客户端保持登录在线**——掉线期间消息不落本地库，两轨一同断流。该轨承担历史导出与无 hook 时的周期增量，本产品核心价值（历史归档）对其依赖最大；4.x 兜底组合已列入 M0 验证（调研报告第九节 #6）；
2. **实时轨为 WeChatFerry**（微信 3.9.12.x）：提供实时回调与（可选的）发送能力；**前置依赖 P0 技术验证**——小号实测 3.9.12 可登录性（当前腾讯对新号/新设备拒登 3.9.x），失败则实时预警降级为小时级准实时；
3. 所有非官方接入均有封号风险：本产品以「收」为主、发送默认关闭、验证一律使用小号；
4. 微信 4.x 客户端暂不在支持范围，跟随 WeChatDataAnalysis / DbkeyHook 等工具生态演进评估。

## 9. MVP 验收标准

1. 成功导入 ≥3 个月历史消息（白名单业务群 + 采集号单聊），抽样 200 条与客户端人工核对：文本类内容/时间/发送者一致率 100%；媒体/引用/撤回/系统等类型 ≥98%，全部差异有清单与原因归类；
2. 群→客户映射完成后，客户列表与会话浏览器数据分区正确（单聊/群聊无串扰）；
3. 组合检索（关键词 + 时间 + 类型）在 10 万条数据量下 <2s；
4. 活跃度统计与人工抽样统计误差为 0（口径：自然日消息条数）；
5. 全部页面在 Chrome/Edge 最新版可用，账号权限按角色隔离生效。

## 10. 风险与开放问题

| 风险/问题 | 影响 | 对策 |
|---|---|---|
| 3.9.x 登录窗口关闭 | 实时轨（F1-3）与发送（F8）不可用 | 架构已按「DB 解密为主」设计，预警降级为准实时；发送永久可弃 |
| 采集端封号 | 该微信号数据源中断 | 小号/工作号专用、以收为主、发送默认关；预留多采集端扩展 |
| DB 结构随微信版本变化 | 解密工具失效 | 版本组合固化不升级；关注 WeChatDataAnalysis/DbkeyHook 演进 |
| 员工隐私与合规争议 | 制度风险 | 内部知情制度、数据最小化、权限隔离；不采集与分析无关的个人社交内容（可按会话白名单采集） |
| 已决策：单聊采集范围（v0.2） | 隐私边界 | MVP 仅归档白名单业务群 + 采集号自身单聊；员工个人账号单聊不采集（多采集端为 V2+ 评估项，见 3.1） |
