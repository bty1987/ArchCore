## 1. 文档定位

文档链的最后一环：前面回答了「为什么做/做什么/怎么设计/怎么开发」，本文回答**怎么稳定运行**（运维）与**怎么走向客户**（推广）。

**本系统运维的特殊性**（区别于普通 Web 应用，决定全文）：运维对象不止是服务器，还有两个「活体」——

1. **Windows 采集主机上的微信客户端**：会掉线、会弹强制升级、登录需人扫码，是持续照料的对象而非一次性部署；
2. **微信账号本身**：账号是被风控的资产，封号 = 数据源中断，必须按资产管理思维建台账、备预案。

## 2. 运维规划

### 2.1 环境与部署形态

| 环境 | 形态 | 用途 |
|---|---|---|
| 开发环境 | 开发机 + fixtures 数据 | 日常开发，永不接触真实会话数据 |
| 演示环境 | 独立主机/虚拟机 + gen-fixtures 数据 | 售前演示，数据全部合成（见 3.4） |
| 生产环境 | 单机 all-in-one（WeChat + collector + server + SQLite） | 每客户一套；V1 起平台可迁内网 Linux，采集端固定 Windows |

原则：**一套客户 = 一套独立部署**（内网化产品的天然形态），不做多租户 SaaS——既规避会话数据集中存储的合规风险，也简化每客户的安全边界。

### 2.2 监控体系（三层）

| 层 | 监控项 | 手段 |
|---|---|---|
| 产品内建（已有需求） | 采集心跳、同步任务、预警流水 | F1-5 采集管理页 + 采集异常预警（红，通知系统管理员） |
| 主机层 | 进程存活（server/collector）、磁盘余量（media/ 是增长大头）、内存 | NSSM/任务计划做进程守护 + 简单巡检脚本告警到企微 |
| 业务层 | 每日消息量趋势突变（骤降 = 采集或群静默）、双轨对账差异 | analysis 任务日检，差异超阈值告警 |

### 2.3 日常运维日历

| 周期 | 动作 |
|---|---|
| 每日（自动） | 备份脚本（SQLite 单文件 + media/ 增量）、巡检脚本、产品内建巡检 |
| 每日（人工 5 分钟） | 看一眼采集管理页：心跳绿、昨日消息量正常、无待处理红预警 |
| 每周 | 检查微信客户端有无升级弹窗/自动升级迹象；查看对账视图 |
| 每月 | 恢复演练（拿最近备份在备用机跑通登录+检索）；账号台账复查；磁盘容量评估 |
| 每季度 | 密钥/token 轮换；审计日志抽查；微信版本动态过一遍（**只评估不升级**，见 2.5）；备份恢复演练重做一次（见 2.4） |

### 2.4 备份与恢复

- **内容**：SQLite 数据库文件 + `media/` 目录 + `config.yaml`（含密钥，备份介质本身需加密保管）；
- **目标**：RPO ≤ 24 小时（每日备份；重要客户可调每小时增量）；RTO ≤ 2 小时（备用机装微信 **4.1.8.67** + Python + 恢复备份 + 扫码登录）；
- **存放**：本机 + 内网异地（NAS/另一台机器）双份；禁止上传公有云盘（数据红线）；
- **演练**：每月一次真实恢复（见 2.3），备份没验证过 = 没有备份。

### 2.5 版本冻结与升级策略（核心策略）

**默认状态：一切冻结。** 微信客户端版本、采集工具版本、Python 依赖版本，全部锁定并在《采集管理页》登记（MVP-503 交付项）。

升级被视为**重大变更**，仅在两种情况触发：① 当前组合彻底失效（拒登/解密失败且无回滚手段）；② 安全性问题必须跟进。升级流程：开发环境用小号验证新组合 → 全量备份 → 生产窗口期内升级 → 双轨对账确认数据无损 → 回填版本登记。任何「顺手升级」都禁止。

**离线安装包常备**：微信 **4.1.8.67** 安装包、仓库各版本快照、Python 安装器，存于内网固定目录——新客户部署和故障回滚都靠它，不依赖外网下载渠道（腾讯下载页只保留最新版，且**当前路线的解密管线随版本变化会失效**，离线包是回滚的唯一手段）。

### 2.6 故障 Runbook

| 故障 | 现象 | 处置 |
|---|---|---|
| 微信掉线 | 采集异常预警；心跳停滞 | 现场扫码重登（**运维唯一需要人在场的场景**，交付时告知客户）；频繁掉线 → 检查主机休眠/RDP 断开策略，改为常亮不锁屏 |
| 微信被自动升级 | 解密 HMAC 异常率高 / 表结构不符 / incr_sync 连续报错 | 卸载 → 离线包回滚 **4.1.8.67** → 删除 `data/wechat4_key.json` → 重新登录后重跑解密（详见[本机部署指南](local-deploy-guide.md) 12.2）；同步确认自动更新处于关闭状态 |
| 解密取钥失败（无内存密钥候选） | 解密工具首步报错 | ① 微信是否已登录且在运行；② 终端是否管理员；③ `Weixin.dll` 是否被更新（版本变了则内部密钥位置变）；确认升级过则同上条回滚 |
| 上报通道异常 | 管道仪表「最近失败」有错误日志 | 服务端未启动或 token 不符；采集端 outbox 会退避重试，恢复后自动冲刷（零丢失） |
| 磁盘告急 | 主机层告警 | media/ 归档旧媒体（按 PRD 保留策略），扩容前先清理同步暂存队列 |
| 通知不达 | 客户说没收到预警 | 预警中心看 notify_record 状态：企微 webhook 用「测试」按钮定位（token 过期最常见） |
| 外发失败率告警 | 外发看板失败率超阈值（仅 send_enabled 开启的部署存在） | 检查工单队列与采集号登录状态（见主动推送方案 4.4） |
| 双轨对账差异大 | 业务层告警 | 优先怀疑某轨漏采：按 session 抽样比对，定位到具体会话后按 Runbook 上两条处置 |

### 2.7 微信账号资产管理

**台账字段**（随部署交付建立，一客户一表）：账号 / 实名归属人 / 注册时长 / 常用设备 / 历史风控记录 / 角色（采集主号、备用号）/ 状态（在用、休养、退役）/ 外发预算使用量、最近熔断时间（仅 send_enabled 开启的部署）。

**用号纪律**：采集号专用（不混个人社交）、加入目标群后**静默只收不发**、新号先在 4.x 正常使用 2~4 周再尝试入列（降低拒登概率）、不发消息不给登出。

**换号 SOP**（封号/拒登时执行）：启用台账中的备用号 → 备用号提前已被拉入全部目标群潜伏（**关键前置：部署时就把备用号拉进群，宁备勿用**）→ 配置切换重新登录 → 会话 wx_id 与映射不变，数据无缝续采 → 退役号登记原因归档。整套动作目标 30 分钟内完成。

### 2.8 安全运维

token/密码季度轮换；审计日志（导出/处理/映射变更）每月抽查；服务器只绑内网；跨网段访问一律走 Nginx + TLS；发现异常访问 → 停服排查，宁可中断不可泄漏（会话数据是客户最高敏资产）。

## 3. 推广规划

### 3.1 三阶段路径

| 阶段 | 对象 | 商务条件 | 目标与退出标准 |
|---|---|---|---|
| 阶段 0：内部试点 | 自己公司/团队的真实业务 | 无 | dogfooding 验证 PRD 全场景；产出内部案例（脱敏截图 + 效率数据，如「每月节省 X 小时整理」「抓住 Y 次响应超时」）；退出 = 内部连续用满 1 个月且预警处理率 > 50% |
| 阶段 1：种子客户 | 3~5 家关系老客户（不同行业，覆盖场景文档的不同规模画像） | 免费/成本价，签试点协议 | 换三样东西：真实环境反馈、可对外引用的案例授权、转介绍承诺；退出 = ≥2 家转正式付费 + 案例成文 |
| 阶段 2：商业化 | 老客户转介绍为主 | 正式定价与合同 | 建立可复制的交付流程（见 3.6），交付周期稳定 ≤ 1 周 |

路径逻辑：内网部署型产品没有线上获客渠道，**口碑与转介绍是唯一规模化通道**，所以阶段 1 的案例质量重于客户数量。

**目标客群修正（v0.2）**：场景文档覆盖个体商户到连锁多业态，但当前交付形态（常开 Windows 采集主机 + 内网部署 + 年度维保）只匹配**有基础 IT 条件的中小企业及以上**；个体商户/一人工作室暂不作为目标客群，待出现轻量托管形态再评估。

### 3.2 售前材料清单（产出责任人：阶段 0/1 期间同步完成）

| 材料 | 内容来源 |
|---|---|
| 一页纸产品介绍 | 场景文档第十一/十二节定位话术：「让每一条客户消息，都变成企业可以理解和经营的业务资产」 |
| 15 分钟演示脚本 | 固定动线：客户痛点提问（场景文档八类问题选 2 个）→ Demo 环境演示检索/客户详情 → 现场触发一条预警到企微（最有冲击力环节）→ 交付方式说明 |
| 常见问题 FAQ | 封号风险怎么控（专用号+只收不发+备用号 SOP）、数据在哪（全程客户内网，我们不带走的承诺）、员工会不会抵触（知情与权限设计）、微信升级了怎么办（冻结策略） |
| 交付边界与免责条款模板 | 见 3.5 |
| 预期管理口径（红线，v0.2 新增） | 一页纸/话术只承诺 V1 可交付能力（归档/检索/映射/分析/预警）；场景文档中的 AI 提取意向、智能助手、自动摘要等属 V2+ 愿景，对外材料须标注「规划中」，不得作为当期卖点 |

### 3.3 演示环境

独立环境 + `gen-fixtures.py` 合成数据（预置 2~3 个虚构客户、数月消息量、若干预警），**永不使用任何真实客户会话数据做演示**——这既是红线也是卖点（可直接写进售前话术）。

### 3.4 定价建议

| 项 | 建议 | 理由 |
|---|---|---|
| 模式 | 一次性部署实施费 + 年度服务费 | 内网部署 + 持续运维（2.3 日历）天然匹配订阅制维保 |
| 计价单位 | 按「管理用户数 + 归档群数」阶梯，不按消息量（v0.2 修订） | 一机一号的物理约束下多数部署仅 1~2 个采集号，按账号数计价无梯度；群数/用户数才贴成本结构与价值感知；按消息量会激励客户省着用，与产品价值背道而驰 |
| 服务费内涵 | 运维日历全部动作 + 换号保障 + 版本冻结维护 + 备份 | 让客户理解「年度费买的是持续可用」，避免被压成一次性买卖 |
| 合同必备 | 合规免责条款（客户确认采集范围与知情义务）、数据归属条款（数据归客户，服务商不留存）、账号风险条款（封号属第三方风控，服务义务为按 SOP 换号恢复） | 场景文档第十四节底线的合同化 |

### 3.5 交付流程（标准化，目标 ≤ 1 周）

售前评估（确认群规模/账号条件/主机条件）→ 环境准备（离线包部署 + 微信 3.9.12 + 账号入群潜伏）→ 历史导入 → 映射初始化（与客户一起把群认领到客户档案，半天工作坊形式）→ 培训（管理员 2h + 员工宣讲 30min，含知情沟通）→ 试运行 2 周观察 → 验收。

### 3.6 运营指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 采集可用率 | > 99%（按月） | 心跳中断时长口径 |
| 预警处理率 | > 70% | 无人理的预警 = 骚扰，必须调规则而非硬推 |
| 周活跃管理用户 | 客户方管理者每周至少 3 天打开 | 推广期最真实的价值信号 |
| 试点→付费转化 | ≥ 60% | 定价与价值验证 |
| 续费率 | > 90% | 维保模式健康的底线 |

### 3.7 对外沟通底线（全文引用场景文档第十四节，售前售后一体遵守）

不把自动发送当卖点；不宣传群发/加好友/营销自动化；不承诺绕过平台限制；不承诺账号永封风险为零；不做未经人工确认的对外触达。**话术口径：我们卖的是「理解、沉淀、分析、提醒」，不是「替你自动聊」。**
